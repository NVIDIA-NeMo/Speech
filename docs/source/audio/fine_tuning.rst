Training and Fine-Tuning
========================

Audio models can be trained from scratch or fine-tuned from pretrained weights. Fine-tune a model when your data
differs in noise, reverberation, microphones, audio domain, or desired output.

Training Entry Point
--------------------

All supported model families use ``examples/audio/audio_to_audio_train.py``. Select a configuration and override the dataset
paths and trainer settings:

The example below uses a Lhotse Shar dataset with ``target_recording`` for training and a validation manifest with
``noisy_filepath`` and ``clean_filepath`` keys.

.. code-block:: bash

   python examples/audio/audio_to_audio_train.py \
       --config-name=predictive_conformer \
       model.train_ds.shar_path=/path/to/train_shar \
       model.validation_ds.manifest_filepath=/path/to/validation.json \
       trainer.max_steps=10000 \
       trainer.limit_train_batches=1000 \
       trainer.val_check_interval=1.0 \
       trainer.devices=1 \
       trainer.max_epochs=-1

The script trains the model and, when ``model.test_ds`` is present, tests it on one device after training. See
:doc:`Configuration Files <./configs>` for the available configurations and :doc:`Datasets <./datasets>` for supported
data formats.

Fine-Tune a Pretrained Flow Matching Model
------------------------------------------

The ``flow_matching_generative_finetuning`` configuration can initialize from the public
``nvidia/sr_ssl_flowmatching_16k_430m`` checkpoint or from a local ``.nemo`` file produced by the pretraining
configuration below. Its encoder, estimator, and flow dimensions match the public checkpoint. Changing those
dimensions can prevent the weights from loading.

A pretrained model can be adapted with either:

* paired degraded and clean recordings; or
* clean recordings whose degraded inputs are generated by the Lhotse loader during training.

Use a fixed paired validation set for both approaches so that validation metrics are comparable between runs. The
public checkpoint and its fine-tuning configuration operate at 16 kHz.

The commands below initialize directly from the public checkpoint. The supplied configuration already contains an
``init_from_nemo_model`` key, so the first override removes it before the second adds
``init_from_pretrained_model``. To use a local checkpoint instead, replace those two overrides with
``init_from_nemo_model=/path/to/model.nemo``.

Paired Training Data
~~~~~~~~~~~~~~~~~~~~

The fine-tuning configuration directly accepts manifests with ``noisy_filepath`` and ``clean_filepath`` keys. Override
``input_key`` and ``target_key`` under ``model.train_ds`` and ``model.validation_ds`` when the manifests use different
names.

.. code-block:: bash

   python examples/audio/audio_to_audio_train.py \
       --config-name=flow_matching_generative_finetuning \
       '~init_from_nemo_model' \
       '+init_from_pretrained_model=nvidia/sr_ssl_flowmatching_16k_430m' \
       model.train_ds.manifest_filepath=/path/to/train.json \
       model.validation_ds.manifest_filepath=/path/to/validation.json \
       trainer.max_epochs=10 \
       trainer.devices=1

Clean Training Data with Online Augmentation
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

For clean-only training data, first create a Lhotse CutSet in which the clean recording supplies both the input and the
``target_recording`` field. The conversion manifest must contain two fields that point to the same clean file:

.. code-block:: json

   {"clean_input_filepath": "audio/clean.wav", "clean_target_filepath": "audio/clean.wav", "duration": 3.147}

Convert that manifest with:

.. code-block:: bash

   python scripts/audio_to_audio/convert_nemo_to_lhotse.py \
       /path/to/clean_train.json \
       /path/to/clean_train_cuts.jsonl \
       --input_key clean_input_filepath \
       --target_key clean_target_filepath

When fine-tuning the public checkpoint, prepare the clean recordings at 16 kHz before conversion. The Lhotse loader
resamples the cut's main recording but does not resample the custom ``target_recording`` field.

Switch ``model.train_ds`` from the configuration's NeMo manifest loader to this CutSet, then choose how to degrade the
input. The command below always adds noise and applies a synthetic RIR to half the examples:

.. code-block:: bash

   python examples/audio/audio_to_audio_train.py \
       --config-name=flow_matching_generative_finetuning \
       '~init_from_nemo_model' \
       '+init_from_pretrained_model=nvidia/sr_ssl_flowmatching_16k_430m' \
       '~model.train_ds.input_key' \
       '~model.train_ds.target_key' \
       '~model.train_ds.manifest_filepath' \
       '~model.train_ds.audio_duration' \
       '~model.train_ds.random_offset' \
       '+model.train_ds.use_lhotse=true' \
       '+model.train_ds.cuts_path=/path/to/clean_train_cuts.jsonl' \
       '+model.train_ds.truncate_duration=6.14' \
       '+model.train_ds.truncate_offset_type=random' \
       '+model.train_ds.noise_path=/path/to/noise_cuts.jsonl' \
       '+model.train_ds.noise_mix_prob=1.0' \
       '+model.train_ds.rir_enabled=true' \
       model.validation_ds.manifest_filepath=/path/to/validation.json \
       +trainer.use_distributed_sampler=false \
       trainer.max_epochs=10 \
       trainer.devices=1

The command removes fields used only by the NeMo manifest loader before adding the Lhotse CutSet and augmentation
fields.

Online augmentation changes the input recording while preserving ``target_recording`` as the clean target. Recorded
RIRs, low-pass resampling, codec augmentation, and clipping or saturation can be configured in the same data section;
see :ref:`lhotse-audio-augmentation`.

If only clean validation audio is available, use ``examples/audio/save_augmented.py`` once to create a fixed paired
validation set rather than sampling new degradations on every validation pass. Each input cut must be a simple mono cut
with a ``target_recording`` field, its main recording path must be relative to the CutSet manifest, and the parent
directory of ``output_cuts`` must already exist. The script applies the augmentations enabled under ``model.train_ds``
and writes a new CutSet with FLAC recordings:

.. code-block:: bash

   python examples/audio/save_augmented.py \
       +input_cuts=/path/to/clean_cuts.jsonl \
       +output_cuts=/path/to/augmented/cuts.jsonl \
       ++model.train_ds.rir_enabled=true \
       ++model.train_ds.rir_path=/path/to/rir_recordings.jsonl \
       ++model.train_ds.noise_path=/path/to/noise_cuts.jsonl

Pretrain a Flow Matching Model
------------------------------

``flow_matching_generative_ssl_pretraining.yaml`` learns to reconstruct spectrogram patches that are masked by
:class:`~nemo.collections.audio.modules.ssl_pretrain_masking.SSLPretrainWithMaskedPatch`. It trains on an unlabeled
Lhotse Shar dataset. The validation manifest uses ``clean_filepath`` as both its input and target.

.. code-block:: bash

   python examples/audio/audio_to_audio_train.py \
       --config-name=flow_matching_generative_ssl_pretraining \
       model.train_ds.shar_path=/path/to/unlabeled_shar \
       model.validation_ds.manifest_filepath=/path/to/validation.json

After pretraining, set ``init_from_nemo_model`` in ``flow_matching_generative_finetuning.yaml`` to the resulting
``.nemo`` file and train on paired degraded and clean audio. Do not change the encoder, estimator, or flow dimensions
unless the corresponding weights are excluded when the checkpoint is loaded.

Before Training
---------------

The sample rate returned by the loader and the channel layout must match the model configuration. The NeMo manifest
loader resamples input, target, and reference signals to the configured sample rate. The Lhotse loader resamples the
cut's main recording, but custom ``target_recording`` and ``reference_recording`` fields must already use the expected
sample rate. Leave the dataset's ``sample_rate`` absent or ``null`` to inherit ``model.sample_rate``. Set ``input_key``,
``target_key``, and channel selectors to the fields and signals present in the manifest; see :doc:`Datasets
<./datasets>`.

Validation metrics for generative models run the sampler and can be substantially slower than validation loss. Use
``max_utts_evaluation_metrics`` to cap the number of validation examples passed to those metrics.
